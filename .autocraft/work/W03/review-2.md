## Findings

[MAJOR] household.removeMember {removeOwnRules:true} is not safe and untested (Operations.swift lines ~46-57). It removes the member's rules first and calls households.removeMember afterwards. If removeMember then throws (the only active member: SafetyTransitionError.lastMember; or a deleted/unknown id), the rules are already gone and the error is returned. For a sole remaining member in `stated` status, Household.removeRule flips them to `confirmedNone` (safetyConfirmedAt = now), so the gate opens with a still-present member whose allergies were deleted, with no `confirmed` flag and no gate re-evaluation in the response (the error path). The removal is also not atomic across several rules (a failure mid-loop leaves a partial deletion). It bypasses the `confirmed:true` that safety.removeRule requires. Fix: validate first (member exists, not deleted, active member count > 1) before touching any rule, or better call removeMember first and then remove the now-orphaned rules (soft-deleted member covers nobody, so the order is safe and a lastMember error changes nothing). Also require the same explicit confirmation or document why not. Add tests: (1) 2 members, rules scoped only to B, household rule, A's rule: remove B with removeOwnRules -> only B's rules gone, household/A rules intact, gate/recheck correct; (2) sole member with a rule: removeOwnRules:true -> error AND the rule still exists and gate unchanged; (3) unknown member id leaves rules untouched. Currently grep shows no test uses removeOwnRules at all.

[MINOR] The report describes removeOwnRules as same order as iOS OnboardingModel.applyCounts; I did not re-read iOS files per the brief, but iOS only reaches this path after the UI guarantees >1 member. The facade has no such guarantee, hence the MAJOR.
